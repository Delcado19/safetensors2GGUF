## [Unreleased]

### Add
- **Text Encoder Support table** on the Model Support tab: a second, compact `gr.Dataframe` below the per-architecture table, covering the formats `Convert Text Encoder` offers (GGUF collapsed from F32/F16/BF16/Q8_0 + K-quants, plus FP8/FP8_MIXED/NVFP4/NVFP4_MIXED). Text encoders aren't in `models.architectures.arch_list` and have no `keys_hiprec`-style per-architecture risk model, so this is one generic row rather than per-architecture columns (`model_support.TEXT_ENCODER_TABLE_FORMATS`/`TEXT_ENCODER_SUPPORT`). Every format is currently `⚠ Caution`: none has a documented ComfyUI load+render confirmation by this project. Clicking a cell jumps to the Convert Text Encoder tab with that format pre-selected (`gui.apply_text_encoder_support_table_selection()`) — unlike the diffusion-model table, NVFP4 isn't excluded here since it's a real `TEXT_ENCODER_FORMAT_CHOICES` entry.

### Change
- **Model Support table split its "Caution" symbol into two states**: `⚠ Caution` (technically supported, not render-tested for this architecture — no evidence either way) previously also covered actually-confirmed-wrong combinations, making the table unable to distinguish "never tried" from "tried and broke". Added `SUPPORT_BAD`/`✗ Known issue` for combinations with direct render-test evidence of wrong output (`model_support._RENDER_CONFIRMED_BAD`): plain `INT8` on `lumina2`, and `NVFP4`/`NVFP4_MIXED` on `lumina2` (docs/issues_analysis.md #15). The format-dropdown ⚠ annotation (`gui.py`'s `_annotate_choices_for_arch()`) now prefixes ✗ for these same combinations instead of silently losing its warning marker.

### Fix
- **Plain FP8 on `lumina2` is now marked `✗ Known issue`, not `⚠ Caution`**: a same-seed/prompt comparison of Z-Image Base output (uncompressed vs. this tool's plain `FP8`) showed the standing figure's outfit and the entire room background changed between the two renders, with only the figures' poses staying recognizable — the same "wrong identity/composition, pose skeleton survives" corruption pattern `docs/issues_analysis.md` #15 documented for pre-fix FP8_MIXED and plain INT8. `model_support._RENDER_CONFIRMED_BAD` and `safetensors_quant._RENDER_CONFIRMED_BAD_PLAIN` now include `("lumina2", "FP8")`; `format_recommendation()`'s warn message states the corruption as confirmed rather than merely predicted by analogy from INT8's confirmed case. FP8_MIXED's status is unaffected — only plain FP8 was exercised by this comparison.

- **The 7th tab ("Model Support") got hidden behind Gradio's "..." tab overflow menu** on real-world renders (Windows/Brave font-fallback rendering measures noticeably wider than in-CI Chromium) — `.gradio-container` widened from 1100px to 1600px and the double-space after each tab's leading icon trimmed to single-space, giving the tab-nav enough room that Gradio's own width measurement keeps every tab on one row instead of auto-collapsing the last two.

- **FP8 wrongly inherited INT8's lumina2 render-verified status**: the previous review fix's shared FP8/INT8 branch in `format_recommendation()` reused `_RENDER_VERIFIED_ARCHES` unconditionally, so `lumina2` + FP8/FP8_MIXED silently inherited INT8_MIXED's actual render-test evidence — plain FP8 claimed "has shown visible pose/identity corruption in testing" (an INT8-only finding) and FP8_MIXED dropped its unverified caveat, both contradicting `model_support.py`'s FP8/FP8_MIXED=`SUPPORT_CAUTION` (no FP8 output from this tool has ever been render-tested). `verified` is now INT8-only. Found by an independent codex-mcp review pass.

- **Final whole-branch review findings for the Model Support tab** (see `docs/superpowers/plans/2026-08-10-model-support-tab.md`):
  - `gui.py` had a mid-file `from model_support import ...` violating the project's `ruff` E402 CI gate — moved to the top-level imports.
  - The Model Support table's NVFP4/NVFP4_MIXED cells were clickable and, via `apply_support_table_selection()`, set the Safetensors format dropdown to a value outside its own `SAFETENSORS_DTYPE_CHOICES` — silently letting a user reach NVFP4 output through the GUI despite it being deliberately unoffered (no verified safe mode, `docs/issues_analysis.md` #16). Those cells are now a no-op, like the Model-name column.
  - `format_recommendation()`'s FP8 branch returned an unconditional "ok" for every architecture, but `quantize_tensor_st()` only skips keys_hiprec-sensitive tensors when `mixed=True` — identically for FP8 and INT8 — so plain FP8 carried the same sensitive-architecture precision risk plain INT8 already warns about. FP8 now shares INT8's sensitivity-aware warn/ok logic.
  - `model_support.support_level()` marked FP8/FP8_MIXED `SUPPORT_VERIFIED` unconditionally, but that status is defined as an actual convert+load+render confirmation in ComfyUI — FP8's safety fix rests on a code-reading investigation only, no render test has confirmed it on any architecture. Downgraded to `SUPPORT_CAUTION` (same bar as NVFP4) until that test happens.
  - `build_support_table()` did a bare `MODEL_DISPLAY_NAMES[...]` index that would crash the entire GUI at startup if a future architecture were added without a matching display-name entry; now falls back to the raw arch key via `.get()`.
  - `quantize.py`'s `ALL_QUANT_CHOICES` comment claimed its size-savings percentages were "derived from `SIZE_RATIOS`", but they're hand-written literals with nothing enforcing the two stay in sync — comment corrected, and a new test (`tests/test_quantize.py::test_size_savings_percentages_match_size_ratios`) now checks the numbers against `SIZE_RATIOS` directly.
  - `_RENDER_VERIFIED_ARCHES` was defined independently in both `safetensors_quant.py` and `model_support.py`, "mirrored" by comment only — `model_support.py` now imports the one in `safetensors_quant.py` instead of keeping its own copy.
  - `st_src_path.change()` fired two separate handlers (`update_format_recommendation`, `annotate_safetensors_choices`) that each independently re-detected the source architecture (a full `torch.load()` for non-safetensors sources); merged into one `update_format_recommendation_and_choices()` handler that detects once.
  - `annotate_gguf_choices()` paid the same full detection cost on every GGUF-tab source-path change for a result that's mathematically guaranteed to never differ from the unmodified choices (`support_level()` has no per-architecture GGUF branch) — now skips detection entirely.

- **Convert → Safetensors intro text was stale**: it still said "FP8/NVFP4/MXFP8 are not offered here", left over from before FP8/FP8_MIXED were re-enabled in the dropdown. Now explains FP8's `full_precision_matrix_mult` safety flag and clarifies that only NVFP4/MXFP8 remain unoffered.

- **FP8 safetensors output took ComfyUI's risky dynamic-activation-quantization path, unlike the scaled-FP8 checkpoints already circulating on Civitai/HuggingFace** — `comfy/utils.py`'s `convert_old_quants()` (how ComfyUI loads those legacy community checkpoints) sets `"full_precision_matrix_mult": true` for them, which makes `comfy/ops.py`'s `MixedPrecisionOps.Linear.forward()` skip the quantized-compute branch and run a plain full-precision matmul instead; this tool's own `convert_safetensors.py` never set that flag. `convert_to_safetensors()` gained a `full_precision_fp8: bool = True` parameter that now writes `"full_precision_matrix_mult": true` into every FP8/FP8_MIXED layer's `.comfy_quant` config by default, matching that same safety profile architecture-independently (unlike INT8's per-architecture `keys_hiprec` bet). See `docs/issues_analysis.md` #16. NVFP4's equivalent investigation (whether it has any comparable safe-mode flag) is explicitly **not done** — open follow-up, `model_support.py`'s `support_level()` docstring keeps NVFP4/NVFP4_MIXED at `SUPPORT_CAUTION` everywhere pending it.

- **`format_recommendation()`'s plain-INT8 warning overclaimed for unverified architectures**: it asserted "plain INT8 has shown visible pose/identity corruption in testing" uniformly for every architecture with a non-empty `keys_hiprec`, but only `lumina2` has actually been render-tested this way. Now mirrors the `ok` branch's existing honesty split: `lumina2` keeps the strong claim, every other sensitive architecture gets a claim scoped to what's actually known (the same class of risk caused corruption on `lumina2`, not confirmed by a render test on this architecture).

Entries stay fully selectable — this only adds information, it never blocks a choice. `gui.annotate_safetensors_choices()`/`gui.annotate_gguf_choices()`, wired as additional `.change()` handlers on `st_src_path`/`src_path` alongside the existing format-recommendation and size-estimate handlers.

The GGUF column collapses every K-quant level into one cell, so it always pre-selects `Q4_K_M` (the tool's own "recommended ★" default); clicking the Model-name column is a no-op.
- **New "Model Support" GUI tab**: renders `model_support.build_support_table()` as a read-only `gr.Dataframe(datatype="html")` — one row per detectable architecture, one colored ✓/⚠/? cell per `TABLE_FORMATS` column (`gui._support_table_cell_html()`/`gui._support_table_rows_for_dataframe()`), reusing the existing `--s2g-accent`/`--s2g-warn`/`--s2g-muted` CSS tokens, plus a legend explaining the tri-state scheme. The other six tabs gained explicit `id=0..5` and the `gr.Tabs()` context is now captured as `main_tabs`, both needed by the next task's click-to-apply wiring (jump to a Convert tab with the clicked format pre-selected).
- **Per-architecture format support table in `model_support.py`**: `build_support_table()` returns one dict row per models.architectures.arch_list entry with architecture name, display name, and support level for each TABLE_FORMATS column — ready for the GUI's Model Support tab (Task 6) to render directly without re-deriving per-architecture sensitivity itself.
- **Per-architecture format recommendation in Convert → Safetensors**: mirrors the GGUF tab's static "recommended ★" label on `Q4_K_M`, but per-architecture — unlike GGUF K-quants (a uniform quality/size tradeoff), plain INT8 measurably corrupts output (wrong poses/identities) on attention-sensitive DiT architectures that need `keys_hiprec` protection, while costing nothing to recommend on architectures that don't need it. `safetensors_quant.format_recommendation(model_arch, target_key)` returns an ("ok"/"warn", message) pair; `gui.py`'s `update_format_recommendation()` detects the source checkpoint's architecture from its header only (no tensor data loaded) and shows a colored badge under the format dropdown, updated on both source-path and format changes. Discloses which architectures' protection lists are actually render-verified (currently only `lumina2`) versus matched against a community reference but not yet confirmed end-to-end, rather than implying uniform confidence. `INT8_MIXED`'s dropdown label also gained the same static "recommended ★" marker as its default-selected status already implied.
- **Automatic Dequantization**: `convert_to_safetensors()` no longer refuses outright when the source checkpoint is already quantized (e.g. a published ComfyUI-native `int8_tensorwise`/ConvRot or scaled-FP8 release) — it now detects each already-quantized `.weight` layer and reconstructs an approximate float32 original before feeding it through the normal quantization pipeline, so it can be cleanly re-quantized to a different target format instead of erroring out (mirrors Starnodes ComfyUI Model Converter's "Automatic Dequantization" feature). New `dequantize.py`: `detect_quantized_weight()` reads the authoritative per-layer `.comfy_quant` JSON sidecar first (falling back to a dtype + sibling-`.weight_scale` heuristic when absent/unparseable — real-world checkpoints don't always carry the sidecar), `dequantize_weight()` reverses `int8_tensorwise` (plain and ConvRot — un-rotates via the Hadamard matrix's orthogonality, `W = W_rot @ H`), scaled FP8, and NVFP4 (reusing the existing `dequantize_nvfp4()`). The old hard guard is narrowed to its one genuinely unrecoverable case: an int8/uint8 `.weight` with no recognizable scale sidecar at all (no scale means no way to reconstruct the original magnitude).

### Correction
- **The FP8_MIXED/NVFP4_MIXED root-cause citation below (Comfy-Org/ComfyUI#14595) was wrong** — read against the issue's own text, it documents a *performance-only* regression (some MLP GEMMs silently fall back to bf16 instead of FP8, ~15% below expected speedup) — mathematically correct output, just slower. It does **not** describe or explain the corruption (black bars, wrong poses/identities, full-image noise) this project observed and root-caused separately. See `docs/issues_analysis.md` #15's Correction note for the full re-examination.

### Fix
- **FP8_MIXED/NVFP4_MIXED diffusion-model output remained visibly wrong (black bars,
  mirrored composition, wrong poses/identities on FP8; full-image noise on NVFP4) even
  after fixing every on-disk data bug in this tool (see the four entries below and
  `docs/issues_analysis.md` #10-#14)** — root cause traced to ComfyUI itself, not the
  file this tool writes. A full weight audit proved the FP8_MIXED file's data 100%
  correct; forcing `full_precision_matrix_mult: true` removed the black bar but not the
  pose/identity drift; protecting `attention.qkv`/`attention.out` via
  `ModelLumina2.keys_hiprec` (confirmed to cover a large fraction of the model's
  parameters, by output file size) changed nothing either. Reading ComfyUI's own
  `comfy/quant_ops.py` `QUANT_ALGOS` registry showed `float8_e4m3fn`/`nvfp4` dynamically
  quantize *activations* at inference time (unlike GGUF, which always dequantizes
  weights to full precision before a standard matmul) through a path with a confirmed
  architecture-dependent bug (Comfy-Org/ComfyUI#14595, filed against a similarly
  new/custom DiT architecture). `int8_tensorwise`/`convrot_w4a4` are the only formats
  ComfyUI marks `"quantize_input": False` — weight-only quantization, sidestepping that
  runtime path entirely. Added `safetensors_quant_int8.py` implementing
  `int8_tensorwise` (single tensor-wise scale, or — where `in_features % 256 == 0` — an
  offline block-Hadamard rotation (ConvRot) plus per-row scale, both algorithms and the
  `.comfy_quant` metadata schema matched against `Comfy-Org/comfy-kitchen`'s and
  `Comfy-Org/ComfyUI`'s published source). Replaced `FP8`/`FP8_MIXED`/`NVFP4`/`NVFP4_MIXED`
  with `INT8`/`INT8_MIXED` in `SAFETENSORS_DTYPE_CHOICES` (the diffusion-model Convert →
  Safetensors GUI tab) — the FP8/NVFP4 implementations stay in the codebase (still
  correct for what they claim to do) but are no longer GUI-selectable given ComfyUI's
  known-buggy consumption path for this architecture family. Text-encoder FP8/NVFP4
  output (a separate registry, `text_encoder_convert.py`) is unaffected/unchanged. See
  `docs/issues_analysis.md` #15.
- **`*_MIXED` safetensors output could end up *larger* than the unquantized bf16 source**:
  `quantize_tensor_st()`'s mixed-hiprec branch force-upcast every protected tensor to
  `torch.float32` regardless of source dtype — harmless while `keys_hiprec` covered only a
  few small tensors, but once extended for Lumina2 (attention + `adaLN_modulation` +
  `final_layer`, see above) this doubled the on-disk size of a large fraction of the model's
  bf16-sourced weights for zero precision benefit (ComfyUI casts every loaded weight to its
  own `compute_dtype` regardless of on-disk dtype). Concretely: `INT8_MIXED` output for a
  12.31 GB source came out at 12.57 GB. Fixed by casting hiprec tensors to their original
  dtype (`data.to(old_dtype)`) instead of a forced F32 — same checkpoint now produces an
  8.30 GB file. Added `test_mixed_hiprec_tensor_keeps_original_dtype_not_forced_f32`. See
  `docs/issues_analysis.md` #15.
- **`ModelLumina2.keys_hiprec` was still narrower than the established community
  consensus for this exact model**: even after protecting attention/modulation/final_layer,
  end-to-end testing (same prompt/seed vs. the unconverted original) showed a
  checkpoint-independent identity/pose difference on both a fine-tune and the official
  `zImageBase_base` checkpoint. `tritant/ComfyUI_Kitchen_nvfp4_Converter`'s published
  `"Z-Image-Base"` blacklist additionally protects `cap_embedder`/`x_embedder`/`t_embedder`/
  `noise_refiner`/`context_refiner` — the submodules that build the initial noise/caption
  representation before the main transformer runs. Added all five (verified against real
  tensor names in a live checkpoint first) and broadened the attention match from
  `"attention.qkv"`/`"attention.out"` to plain `"attention"`. Output size grew from 8.30 GB
  to 8.77 GB (still ~29% smaller than the 12.31 GB source). End-to-end verification (same
  prompt/seed, both a fine-tune and the official checkpoint) confirmed pose/composition/
  identity now closely match the unconverted original. See `docs/issues_analysis.md` #15.
- **Extended `keys_hiprec` for every other architecture this project supports that
  tritant/ComfyUI_Kitchen_nvfp4_Converter also has a published per-architecture blacklist
  for**, since `ModelFlux` and `ModelQwenImage` had *no* `*_MIXED` protection at all and
  `ModelWan`/`CosmosPredict2` had only one tensor each protected — the same class of risk
  Lumina2 turned out to have, just not yet reported for these. `ModelFlux` gains
  `img_in`/`txt_in`/`time_in`/`vector_in`/`guidance_in`/`final_layer`/`class_embedding`/
  modulation tensors; `ModelQwenImage` gains `img_in`/`txt_in`/`time_text_embed`/
  `norm_out`/`proj_out`/`img_mod.1`; `ModelWan` adds `text_embedding`/`time_embedding`/
  `time_projection`/`head`; `CosmosPredict2` (the architecture Anima checkpoints use) adds
  `llm_adapter`/`final_layer`/`proj_out`/`x_embedder`/`t_embedder`/`context_embedder`
  (cross-checked against `Comfy-Org/comfy-quants`' own `anima.md`, which independently
  protects the same set). Not end-to-end image-tested for these four (no checkpoints
  available this session) — adopted on the strength of an established community tool's
  configuration, unlike the Lumina2 fix which was verified against real renders. See
  `docs/issues_analysis.md` #15.
- **Non-mixed NVFP4 crashed on Lumina2's pad-token parameters**: `ModelLumina2.keys_hiprec = ["x_pad_token", "cap_pad_token"]` only protects those tensors under `*_MIXED` targets (`quantize_tensor_st()` only consults `keys_hiprec` when `mixed` is `True`). Under plain `NVFP4`, they got packed like any other 2D tensor, halving their last dimension — and since ComfyUI's `NextDiT.__init__` hardcodes these `nn.Parameter`s to a fixed shape from the detected architecture (unlike `cap_embedder.1.weight`, which corrupts an *inferred* config), the mismatch is a hard crash (`size mismatch for x_pad_token: … [1, 1920] … [1, 3840]`) rather than silently-wrong values. Fixed by adding `"x_pad_token"`/`"cap_pad_token"` to `ModelLumina2.keys_shape_critical`, which — unlike `keys_hiprec` — is checked unconditionally. Added `test_nvfp4_pad_token_falls_back_to_f16_unconditionally`. See `docs/issues_analysis.md` #14.
- **NVFP4 output was nibble-swapped for the real ComfyUI inference kernel, even with every value/scale/layout check passing**: `comfy_kitchen`'s standalone `dequantize_nvfp4()` helper exposes a `hi_first` nibble-order parameter, but the function ComfyUI's real inference path actually calls — `scaled_mm_nvfp4()`, the fused GEMM kernel — has **no such parameter**; its convention is hardcoded to `hi_first=True` (even-indexed element in the high nibble). `safetensors_quant_nvfp4.py`'s `quantize_nvfp4()` packed the opposite way. This was invisible to every dequantize-based check in this investigation — including auditing all 413 weight tensors in a real converted file against the original checkpoint, all found byte/value-correct — because those checks all went through `dequantize_nvfp4()` (either this tool's own, self-consistent by construction, or `comfy_kitchen`'s with `hi_first` set to match). Found only by noticing `ck.scaled_mm_nvfp4`'s signature has no `hi_first` argument at all. Fixed by swapping the packing order; verified directly against `scaled_mm_nvfp4` (not `dequantize_nvfp4`): a weight quantized by this tool now matches a full `comfy_kitchen`-native ground truth matmul to within normal 4-bit×4-bit quantization noise (13.22% vs. 13.01% relative mean error). Added `test_packs_even_index_in_high_nibble_hi_first_true`, which checks a hand-computed packed byte value rather than a round trip. See `docs/issues_analysis.md` #13.
- **Re-quantizing an already-quantized source checkpoint silently corrupted it**: some published checkpoints (e.g. ComfyUI-native `int8_tensorwise`+ConvRot releases) are already partially quantized, storing raw integer weights alongside their own pre-existing `.weight_scale`/`.comfy_quant` sidecar tensors right in the state dict. This tool had no concept of that — it iterated every tensor and re-quantized each one as an ordinary weight, including the pre-existing scale/metadata sidecars themselves (a `[rows,1]` float32 `.weight_scale` tensor looks just like a small 2D weight matrix), producing corrupted output with mis-named `_quantization_metadata` layer keys (an extra `.weight_scale` suffix, since `layer_key()` only strips a trailing `.weight`). Found by tracing a user's FP8_MIXED noise-image report: 170 of 378 layers in the output had corrupted metadata keys, all tracing back to a source checkpoint (`juggernautZ_v10ByRundiffusion.safetensors`) that turned out to already be `int8_tensorwise`-quantized — confirmed by its own embedded `_quantization_metadata`. Fixed by adding `_check_not_already_quantized()` (`convert_safetensors.py`), which raises before conversion starts if any `.comfy_quant` sidecar key is present anywhere in the state dict, or any `.weight` tensor is stored as int8/uint8 (bare float8 weights are still allowed through — an existing, deliberately-supported case, coerced to float16). Verified against both the corrupted source (raises) and a genuinely unquantized sibling file in the same directory (does not raise). See `docs/issues_analysis.md` #12.
- **Every NVFP4 safetensors conversion decoded every weight at exactly half its intended magnitude**: `safetensors_quant_nvfp4.py`'s `_KVALUES` E2M1 decode table used `gguf.quants.NVFP4.kvalues`'s **doubled** magnitudes (`0,1,2,3,4,6,8,12,…`), per its own docstring claim of matching that table. But gguf's table is doubled specifically to compensate for a *different*, custom per-block scale encoding gguf's NVFP4 uses internally (`ue4m3_to_fp32`, which bakes in a `*0.5` decode factor) — this tool never used that encoding, it writes plain `torch.float8_e4m3fn` block scales (what ComfyUI's `comfy_kitchen` actually expects), so pairing that with gguf's doubled table silently halved every decoded weight. Reported by a user as pure-noise/garbage NVFP4_MIXED output persisting even after the shape-crash and swizzle-layout fixes below. This tool's own round-trip tests never caught it — quantizing and dequantizing with the same (wrong) table cancels the error out, only surfacing against ComfyUI's real, independent decoder. Found by comparing `quantize_nvfp4()` output directly against `comfy_kitchen.tensor.nvfp4.TensorCoreNVFP4Layout`'s own quantize/dequantize on a live ComfyUI install: a block filled with the exact table value `6.0` decoded back to `3.0`, showing the 2x error directly. Fixed by replacing `_KVALUES` with the standard undoubled OCP E2M1 magnitudes (`0,0.5,1,1.5,2,3,4,6,…`) — the existing `/6.0` scale divisors already assumed this range. Verified against `comfy_kitchen`'s own reference on a random tensor: mean reconstruction error 0.2857 (ours) vs. 0.2856 (ComfyUI's own). Added `test_kvalues_are_standard_undoubled_e2m1_magnitudes` and `test_block_of_exact_table_values_round_trips_exactly`.
- **Every NVFP4 safetensors conversion produced a `.weight_scale` tensor in the wrong on-disk layout for every 2D (Linear) weight** — not just the one layer a user hit a crash on: `safetensors_quant_nvfp4.py` wrote each layer's `.weight_scale` as a plain, unpadded `(rows, k_blocks)` tensor, but ComfyUI's `comfy_kitchen` CUDA backend (`scaled_mm_nvfp4`) requires block scales padded to `(roundup(rows,128), roundup(k_blocks,4))` **and** rearranged into a 128x4 block-interleaved layout — the same convention vLLM's `swizzle_blockscale()` and TensorRT-Model-Optimizer NVFP4 checkpoints use. Concretely, this means two distinct symptoms depending on the layer's shape, both present in every prior NVFP4/NVFP4_MIXED conversion:
  - Layers whose output width isn't already a multiple of 128 (or block count a multiple of 4) fail the kernel's shape assertion outright — reported by a user as a crash (`AssertionError: Invalid B scale shape`) on Lumina2/Z-Image's `final_layer.linear.weight`.
  - Layers whose dimensions already happen to be multiples of 128/4 (most transformer block weights — hidden_size, mlp_dim, …) pass the shape check, but the scale values are read in the wrong order by the kernel, since a plain zero-padded tensor and the required interleaved layout have the same shape but different element order. This loads silently wrong (not crashing) weights.

  Root-caused by reading `comfy_kitchen`'s CUDA backend source directly (`roundup_n`/`roundup_sk` formula) and cross-verified against vLLM's open-source `nvfp4_utils.py` implementation of the identical layout. Fixed by adding `_swizzle_block_scale()`/`_unswizzle_block_scale()` (2D weights only — the case that reaches this kernel path) to `safetensors_quant_nvfp4.py`, applied unconditionally in `quantize_nvfp4()`. Existing NVFP4 tests updated for the new padded/swizzled `weight_scale` shape; added `test_scale_swizzled_shape_matches_comfy_kitchen_kernel_formula` and `test_swizzle_matches_vllm_reference_implementation` (a literal transcription of vLLM's function, since a self-inverting swizzle/unswizzle round-trip test alone can't detect a layout that's internally consistent but wrong relative to the real kernel).
- **`ensure_plain_llama_quantize()` couldn't actually use an auto-detected Visual Studio on Windows**: `_locate_msvc_build_env()` (added alongside the K-quant feature above, for the common case where VS is installed but its tools were never added to the user's PATH) had two bugs, both found and fixed via a real end-to-end build on a Windows machine with VS installed but nothing on PATH:
  - The `cmd /c "call \"<vcvarsall>\" x64 && set"` invocation used to capture vcvarsall's environment variables failed outright — `subprocess`'s Windows argument-quoting (`list2cmdline`) re-quotes an argument that itself contains both spaces and quotes (the vcvarsall path), mangling the nested quotes so cmd.exe couldn't find the batch file at all (silent `FileNotFoundError`, caught and treated as "no VS found"). Fixed by writing the `call`+`set` sequence to a temp `.bat` file and running that instead — sidesteps the nested-quoting problem entirely.
  - Even with the environment captured correctly, passing it as `subprocess.run(["cmake", ...], env=build_env)` still raised `FileNotFoundError`: on Windows, `env=` only sets the **child** process's environment block — the executable itself is still resolved against the **calling** process's own `PATH`, not `build_env`'s. Fixed by resolving `cmake`'s absolute path via `shutil.which("cmake", path=build_env["PATH"])` before invoking it, instead of relying on Windows to search `build_env["PATH"]` (it doesn't). Added `test_resolves_cmake_absolute_path_from_located_msvc_env` regression test.
- **FP8/NVFP4 safetensors output was silently broken in ComfyUI**: `safetensors_quant_fp8.py`/`safetensors_quant_nvfp4.py` named the per-layer scale sidecar tensor `<full_tensor_name>.weight_scale` (e.g. `x_embedder.weight.weight_scale`), but ComfyUI's quantized-op loader (`comfy/ops.py _load_quantized_weight_body`, confirmed by reading a live ComfyUI 0.29.2 install) looks up `<module_prefix>weight_scale` — a **sibling** of `<module_prefix>weight`, not nested under it (e.g. `x_embedder.weight_scale`). The mismatch meant every `.weight_scale`/`.weight_scale_2`/`.comfy_quant` tensor we wrote was reported by ComfyUI as an "unexpected key" and silently discarded: FP8 checkpoints loaded the raw unscaled float8 bytes as weights (visible as solid-noise output images), and NVFP4 additionally crashed on some checkpoints (see below). Root-caused via a user bug report showing garbage Z-Image output from a `FP8_MIXED` conversion and a `RuntimeError` shape mismatch from `NVFP4_MIXED`. Fixed by adding `safetensors_quant.layer_key()` (strips a trailing `.weight` to get the module prefix ComfyUI expects) and using it consistently for scale-tensor naming and the `_quantization_metadata` "layers" dict key in `convert_safetensors.py`. All existing FP8/NVFP4 tests updated to the corrected naming; added `test_quantization_metadata_layer_key_has_no_weight_suffix` regression test.
- **NVFP4 could corrupt ComfyUI's architecture-hyperparameter detection**: independent of the naming bug above, ComfyUI's `model_detection.py` infers hyperparameters directly from specific tensors' raw on-disk shapes before any dequantization — a pattern used across ComfyUI's supported architectures, not just Lumina2 (e.g. Flux infers `in_channels` from `img_in.weight.shape[1]`, Lumina2 infers `cap_feat_dim` from `cap_embedder.1.weight.shape[1]`). NVFP4 halves a packed tensor's on-disk last dimension (2 values/byte), corrupting that inference and crashing model load — this is a gap in this tool's non-mixed NVFP4 path (which packed those tensors indiscriminately), not a ComfyUI bug: published NVFP4 checkpoints conventionally leave small embedding/patchify layers unquantized anyway. Added `ModelTemplate.keys_shape_critical` (`models/architectures.py`) to exclude flagged tensors from NVFP4 packing unconditionally (not gated by `*_MIXED`, since this is shape-safety, not precision). Audited every architecture against a live ComfyUI install and populated it for `ModelFlux`/`ModelQwenImage` (`img_in.weight`), `ModelSD3` (`context_embedder.weight`), `ModelAura` (`cond_seq_linear.weight`), `ModelLumina2` (`cap_embedder.1.weight`), `CosmosPredict2` (`x_embedder.proj.1.weight`), `ModelHyVid` (`txt_in.input_embedder.weight`), `ModelWan` (`head.modulation`), and `ModelLTXV` (`transformer_blocks.0.attn2.to_k.weight`) — `ModelHiDream` was audited and confirmed to need no fix (its `unet_config` is hardcoded constants, no shape reads). `ModelSDXL`/`ModelSD1` remain unaudited (ComfyUI's `context_dim` detection there scans block indices dynamically rather than reading one fixed tensor name) — see `docs/issues_analysis.md` #9 for the full per-architecture table.
- `gui.py`: The **Convert → Safetensors** tab's output-path Browse button opened a file-*open* dialog (`_browse(_MODEL_TYPES)`, meant for picking a source model) instead of a directory picker.
